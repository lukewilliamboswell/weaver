= weaver 0.10.0

This release changes how arguments after a subcommand are parsed, so a
command line that relied on the old behaviour can now be rejected. It
changes no package APIs.

== Use this release

[source,roc]
----
app [main!] {
    weaver: "{package-url}",
}
----

== Arguments after a subcommand belong to it

Everything after a subcommand's name is now parsed by that subcommand alone.
Before, an argument it did not consume was passed back to its ancestors: an
ancestor's option could be given after the subcommand, and extra parameters
filled the ancestor's parameters.

[source,console]
----
$ subcommands s1 -f
The argument "-f" was not recognized.

Usage:
  subcommands s1 [-d NUM] [-v/--volume NUM] [-h/--help] [-V/--version] [COMMAND]
----

Give an ancestor's options before the subcommand's name instead:
`subcommands -f s1`. An extra parameter after a subcommand is reported as
not expected, against that subcommand's usage. Arguments before the name,
`--` before it, and help or version requests after it behave as before.

== Fixes

* Help for a subcommand path that names an unknown subcommand now shows the
  longest valid part of the path, with a header that matches its content.

== Tooling

* Release SBOMs are generated by roc-automation's shared `sbom-sidecars`
  action, which also writes the evidence envelope. A release now attaches one
  SBOM manifest instead of two.
